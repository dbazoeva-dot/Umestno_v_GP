# UX Telegram-бота @umestno_home_bot — ТЗ на реализацию

Документ описывает **целевой UX бота на стадии «замер спроса»**: сценарии,
экраны, тексты, кнопки, логику веток и изменения в данных. Отдаётся
разработчику как техзадание.

Текущее состояние бота — заглушка с доработками
(`server/workers/telegram.ts`, миграции `0005/0007/0008`). Полноценный
диалоговый калькулятор в боте **пока НЕ проектируется** — сначала
подтверждаем спрос. Но UX и схема данных готовятся так, чтобы принять его
без переделок.

Тон везде: спокойный, заботливый, ясный. Обращение на «Вы» с заглавной.
Без впаривания. Ясность важнее обтекаемых формулировок.

---

## 1. Цели (в порядке важности)

1. **Замерить спрос на расчёт прямо в боте.** Гипотеза владельца: люди
   захотят считать схему в чате, а не на сайте. Ключевая метрика — доля
   нажатий кнопки «Посчитать прямо здесь, в чате» (`wants_bot_calc`) от
   общего числа `/start`. Калькулятора в боте сейчас НЕТ — это сознательно.
2. **Не терять оплаченные касания.** Трафик платный (реклама), каждый
   пришедший оплачен. Обслуживаем все три ветки готовности человека, не
   теряя ни одной.

## 2. Три ветки готовности → три исхода, без тупиков

| Ветка | Кто это | Исход |
|---|---|---|
| **1. Готов сейчас** | знает размеры, хочет результат | увод на сайт `/configure/` (прямая конверсия 149 ₽) |
| **2. Хочет в чате** | хочет считать прямо в Telegram | фиксируем `wants_bot_calc` (замер спроса) + лист ожидания |
| **3. Не готов сейчас** | интересно, но неудобно / нет размеров под рукой | сохраняем связь, один мягкий возврат позже |

**Принципы:**
- **Нет тупиков.** После любого экрана есть понятное следующее действие.
- **«Сохранён» по умолчанию.** Каждый, кто нажал `/start`, уже в
  `bot_subscribers`. Не рассчитываем на клик «подписаться».
- **Демо-сигнал чистый.** «Не готов» — отдельный, более мягкий исход, а не
  та же кнопка, что «хочу в чате» (иначе спрос завышается).
- **Честность на клике.** Кнопка «в чате» зовёт к действию, но в первую же
  секунду честно говорит «пока не готово, Вы в списке первых». Расчёт не
  имитируем, денег за воздух не берём.
- **Сайт-ссылка не исчезает никогда** — даже после запуска чат-калькулятора.

## 4. Экраны (тексты, кнопки, запись в БД)

Обозначения: `▸URL` — кнопка-ссылка на сайт, `●cb` — callback-кнопка.

### 4.1. `/start` — приветствие

- **Текст:** оставить `WELCOME_TEXT` как есть (копирайт владельца, не редактируем).
- **Кнопки:**
  1. `▸URL` «Рассчитать схему под мои размеры →» → `/configure/` с UTM (и `&tg=<id>`, если включён блок §8).
  2. `●cb viewed_example` «Посмотреть пример результата».
  3. `●cb wants_bot_calc` «Посчитать прямо здесь, в чате».
- **БД:** `INSERT/UPDATE` контакт, `source` через COALESCE сохраняет первый, `first_seen_at`.
- **Решение:** четвёртой кнопки «напомнить позже» НЕТ — человек и так сохранён, явный лист ожидания = кнопка «в чате», остальных закрывает напоминание §6. Это держит экран в фокусе и не разбавляет демо-сигнал.

### 4.2. «Посмотреть пример» → `viewed_example`

- **Контент:** фото-пример + `EXAMPLE_CAPTION` (честно: «под Ваш ящик будет своя»).
- **Кнопки (3, FAQ — третьей, чтобы не двигать позиции конверсии и демо-сигнала):**
  1. `▸URL` «Рассчитать схему под мои размеры →»
  2. `●cb wants_bot_calc` «Посчитать прямо здесь, в чате»
  3. `●cb faq:open` «Частые вопросы»
- **БД:** `viewed_example=true, viewed_example_at`.
- Если картинки нет — текстовый fallback с теми же тремя кнопками.

### 4.3. «Посчитать в чате» → `wants_bot_calc`

- **БД:** `wants_bot_calc=true, wants_bot_calc_at`.
- **Текст (вместо текущего, добавлен выход — раньше был мягкий тупик):**
  > Записала Вас в список первых 🌿 Как только расчёт заработает прямо здесь, в чате — сразу напишу сюда.
  >
  > А если ждать не хочется — схему можно собрать на сайте уже сейчас, это те же 3 минуты.
- **Кнопка:** `▸URL` «Рассчитать на сайте →» (тот же UTM). Горячие из листа конвертятся сразу.

### 4.4. Свободный текст / `/help`

- **БД:** помним контакт.
- **Текст (вместо старого, без упоминания `/subscribe`):**
  > Я пока умею немного 🙂 Чтобы собрать схему под Ваш ящик — выберите, как удобнее:
- **Кнопки:** `●cb faq:open` «Частые вопросы» · `▸URL` «Рассчитать схему →» · `●cb viewed_example` «Посмотреть пример» · `●cb wants_bot_calc` «Посчитать в чате».

### 4.5. `/stop` (опт-аут)

- **БД:** `unsubscribed_at=now()`.
- **Текст:**
  > Готово, больше напоминать не буду. Если передумаете — напишите /start, я снова рядом.
- Та же функция вызывается кнопкой `Больше не напоминать` из напоминания §6.

## 5. FAQ — частые вопросы

### Механизм
- **Меню inline-кнопок** (надёжно; распознавание свободного текста на русском
  с опечатками хрупкое — не делаем на старте; точечное распознавание «цены»
  можно добавить позже по логам).
- **Три входа:** под фото-примером (§4.2), фолбэк (§4.4), команда `/help`.
- **На `/start` FAQ НЕ ставим** — там фокус на 3 конверсионных кнопках.
- `callback_data`: `faq:open` (список), `faq:price | faq:engine | faq:result |
  faq:measure | faq:fit | faq:chat`.
- Каждый ответ: короткий текст + action-кнопка по теме + `← К вопросам`
  (`faq:open`).

### Навигация (петля без тупика — критично)

Петля **«пример → FAQ → ответ → Рассчитать/в чате»** обязана замыкаться.
Уязвимое место — сам список вопросов: если из ответа вернуться на список,
а на списке нет действия, человек «варится» между вопросами. Закрываем
тремя гарантиями:

1. **Список вопросов (`faq:open`) сам несёт действия.** Под 6 вопросами —
   `▸URL «Рассчитать схему →»` и `●cb «Посчитать в чате»`. Список не «только
   вглубь»: из него всегда один тап до действия. *(Допустима лёгкая версия —
   на списке только `▸URL «Рассчитать →»`, т.к. путь «в чате» покрыт ответом
   на вопрос 6; но по умолчанию ставим обе.)*
2. **Каждый ответ** несёт action по теме + `← К вопросам`. Двойное покрытие:
   и ответ, и список ведут к действию — застрять негде.
3. **Ответы — отдельными сообщениями, фото-пример НЕ редактируем.** На тап
   «Частые вопросы» и на каждый вопрос бот шлёт НОВОЕ сообщение
   (`ctx.reply`), а не подменяет подпись картинки. Причины (по обратной
   связи владельца):
   - подмена одного сообщения выглядит странно и **«как фрод»** — наши же
     ответы не фиксируются, будто мы прячем обещания;
   - человек может забыть, что бот ответил, и чтобы перечитать, надо жать
     снова;
   - при редактировании подписи фото **картинка-пример визуально
     повторяется** на каждом шаге.
   Отдельные сообщения оставляют весь диалог в истории, картинка показывается
   один раз. Петля всё равно замкнута: у каждого ответа есть action + `← К
   вопросам`, у списка — свои action-кнопки (гарантии 1–2).

URL-кнопка «Рассчитать» во всех узлах FAQ несёт тот же UTM/`source`
(и `&tg` при §8), что и на `/start`.

### Пунктуация

Во всех **новых** текстах бота — русская пунктуация: запятые и двоеточия,
**без длинных тире** (`—`). Исключение — `WELCOME_TEXT` (копирайт владельца,
не редактируем без согласования).

### Контент (10 вопросов; выверено по FAQ лендинга — `app.js → FAQS`)

Ответы сокращены под чат, формулировки и тон совпадают с одобренными на
сайте. Под каждым ответом: action по теме + `← К вопросам`.

1. **Сколько стоит?** (`faq:price`) — 149 ₽ за расчёт, без подписок; не собралась схема — оплаты нет.
2. **Что я получу?** (`faq:result`) — зоны, размеры блоков, памятка по складыванию, органайзеры под блоки; рабочая конфигурация, а не список товаров.
3. **Это просто список органайзеров?** (`faq:notjust`) — нет; сначала схема, товары уже под готовые блоки.
4. **Надо точно считать вещи?** (`faq:counting`) — нет; диапазоны мало/средне/много, остальное считает система.
5. **Как замерить ящик?** (`faq:measure`) — внутренние ширина/глубина/полезная высота; ссылка на blog/kak-zamerit-yashchik.
6. **Чем отличаются режимы расчёта?** (`faq:modes`) — Удобно / Вместительно / Экономично: на что система ставит приоритет.
7. **Можно сохранить результат?** (`faq:save`) — да, скачать или на почту.
8. **Можно использовать свои органайзеры?** (`faq:own`) — да; рекомендации не обязательны, важно сохранить логику схемы.
9. **Что если схема не подойдёт?** (`faq:notfit`) — не собралась → не платите; если куплено и что-то не так → help@umestno-home.ru, проверим/пересоберём/вернём деньги.
10. **Можно посчитать в чате?** (`faq:chat`) — пока на сайте (~3 минуты); записать в список первых (= ВЕТКА 2, питает демо-сигнал).

Точные тексты — в `server/workers/telegram.ts` (`FAQ_ANSWERS`). Кнопки
ответов: обычный ответ → `▸URL Рассчитать схему →` + `← К вопросам`; ответ
про чат → `●cb Посчитать в чате` + `▸URL Рассчитать на сайте →` + `← К вопросам`.

## 6. Удержание неготовых (ветка 3): одно мягкое напоминание

- **Когда:** один раз, на `D+3` после `first_seen_at`. Никаких серий.
- **Кому:**
  `unsubscribed_at IS NULL` AND `wants_bot_calc = false` (эти получат анонс
  запуска, а не напоминание — чтобы не задвоить касание) AND
  `reminder_sent_at IS NULL` AND `converted_at IS NULL` (не купил — см. §8).
- **Текст (value-first, без давления):**
  > Здравствуйте! Это «Уместно» 🌿 Если до ящика пока не дошли руки — он подождёт, спешить некуда.
  >
  > Когда станет удобно, мы за 3 минуты соберём схему хранения под Ваши размеры: где какая зона, как сложить вещи, какие органайзеры подойдут. 149 ₽, без подписок.
- **Кнопки:** `▸URL` «Рассчитать схему →» · `●cb` «Больше не напоминать» (→ `unsubscribed_at`).
- **БД после отправки:** `reminder_sent_at=now()`. Дальше — тишина; бот
  реагирует только на действия самого человека.

> **Важно (см. §8):** без привязки бот↔сайт у нас НЕТ сигнала, что человек
> ушёл на сайт и купил (клик по URL-кнопке боту невидим). Поэтому при
> выключенном блоке §8 либо (а) включаем напоминание с нейтральным к «уже
> купил» копирайтом и принимаем малый риск, либо (б) держим напоминание
> ручным/отложенным до включения §8. Рекомендуется (б) → затем §8 → авто.

## 7. Запуск чат-калькулятора (готовим почву, сам диалог — позже)

- **Feature-flag `CHAT_CALC_ENABLED`** (env):
  - `false` (сейчас): кнопка «Посчитать в чате» = лист ожидания (§4.3).
  - `true` (после запуска): та же кнопка **стартует диалог** (диалог
    проектируется отдельно). Лейбл и `callback_data` те же — меняется только
    обработчик за флагом.
- **Анонс по листу ожидания (разовый broadcast):**
  - Аудитория: `wants_bot_calc = true` AND `unsubscribed_at IS NULL` AND
    `launch_announced_at IS NULL`.
  - Текст:
    > Готово 🌿 Теперь схему можно собрать прямо здесь, в чате — Вы просили сообщить. Пара вопросов про размеры и вещи — и схема у Вас.
  - Кнопки: `●cb` «Собрать схему в чате» · `▸URL` «Или на сайте →».
  - БД: `launch_announced_at=now()`. Это ожидаемое сообщение, не спам.
- **Чтобы готовые не терялись при переходе:**
  - На `/start` после запуска — **две двери**: «Собрать в чате» + «Или на сайте →». Сайт-ссылку не убираем.
  - Любой затык в диалоге → мягкий фолбэк на `/configure/`.

## 8. ⚙️ ОПЦИОНАЛЬНЫЙ блок: привязка бот↔сайт (атрибуция покупок)

> **Можно сделать позже — бот работает и без этого.** Но без блока бот
> «слепой»: не знает, кто из пришедших купил (клик по URL-кнопке Telegram
> боту не сообщает, оплата проходит на сайте). Блок даёт две вещи:
> (1) не писать напоминание тем, кто уже купил; (2) видеть реальную
> конверсию бот→продажа по источникам.

**Идея:** прокинуть `tg_user_id` сквозняком — ровно по тем рельсам, по
которым на сайте уже ездит анонимный `session_id`.

```
бот: кнопка →  /configure/?…&tg=<id>
   → calc.js запоминает tg (как session_id) и кладёт в заявку
   → calculate.ts сохраняет orders.tg_user_id
   → yookassa webhook: оплата прошла → UPDATE bot_subscribers
        SET converted_at=now() WHERE tg_user_id=<id>     ← бот узнал о покупке
```

**Доработка сайта — три маленьких места, всё повторяет существующий `session_id`:**

1. **`/configure/` (фронт, calc.js):** прочитать `?tg=` из URL, сохранить там
   же, где `session_id` (чтобы пережил переходы, в т.ч. `/no-fit/` и обратно),
   приложить `tg_user_id` к POST `/api/calculate`.
2. **`calculate.ts`:** добавить необязательное поле `tg_user_id` в тип
   запроса + одну колонку/параметр в `INSERT INTO orders` (рядом с
   `session_id`). Если `tg` нет — всё работает как раньше.
3. **`yookassa.ts`:** после `UPDATE orders SET status='paid'` — один шаг:
   если у заказа есть `tg_user_id`, то
   `UPDATE bot_subscribers SET converted_at=now() WHERE tg_user_id=$1 AND converted_at IS NULL`.

**Доработка бота:** `buildSiteUrl()` добавляет `&tg=<tg_user_id>` (число,
безопасно для URL).

**Объём:** несколько часов, не дни. Логику расчёта/оплаты не меняем — только
добавляем одно необязательное поле. Риск для существующего флоу минимальный.

**Приватность:** `orders.tg_user_id` — это PII → добавить в 3-летний scrub
`orders` (см. `docs/data-model.md`, раздел Retention) рядом с `session_id`.

**Миграция `0010` (отдельная, на `orders`):**
```sql
BEGIN;
ALTER TABLE orders ADD COLUMN IF NOT EXISTS tg_user_id bigint;
CREATE INDEX IF NOT EXISTS orders_tg_user ON orders (tg_user_id)
  WHERE tg_user_id IS NOT NULL;
COMMIT;
```

## 10. Механика рассылок (напоминание §6 и анонс §7)

- **At-most-once:** сначала `UPDATE … SET reminder_sent_at/launch_announced_at=now()`,
  потом отправка. Краш в середине → человек пропущен (для одного сообщения
  приемлемо), а не получит дубль.
- Выборка батчами через `FOR UPDATE SKIP LOCKED`, темп ~20 msg/s.
- На `429` — backoff по `retry_after`; на `403 (bot blocked)` / деактивирован
  — `UPDATE … SET unsubscribed_at=now()` (чистим список).
- Ходим через тот же `TG_API_ROOT`-прокси, что и long-polling.

## 11. Метрики / воронка

- **Главная (гипотеза владельца):** `wants_bot_calc / total_contacts` в
  разрезе `source` (уже в `/stat`).
- **Поддерживающие:** `viewed_example %`; URL-переходы из Метрики по
  `utm_term=source`; при блоке §8 — реальная конверсия бот→продажа
  (`converted_at`) по источникам.
- **Триггер решения «делаем диалоговый калькулятор»:** порог владельца
  (≥100 `/start`) + доля «в чате» устойчиво выше нуля по нескольким источникам.
- **`/stat` дополнить:** строку `active_subscribers` (теряет смысл после
  выпила `/subscribe`) заменить на «лист ожидания = `wants_bot_calc`»;
  добавить `reminder_sent`, опт-ауты, при §8 — `converted`.
